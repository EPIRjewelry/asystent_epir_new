2) Ocena modyfikacji (dodanie `tool_schema.ts` i jego wstrzyknięcie do `engineer_prompt.ts`)

- Co zrobiono: utworzyłeś `worker/src/mcp/tool_schema.ts` (pełny JSON Schema) i zaimportowałeś `generateMcpToolSchema()` do `engineer_prompt.ts`. `generateGroqPrompt` wypełnia teraz pole `toolSchema` i wstrzykuje zarówno `OPTIMIZED_TOOL_DEFINITIONS`, jak i `data.toolSchema` do promptu.

- Zalety modyfikacji:
  - Większa ścisłość: model otrzymuje formalny schemat narzędzi (przydatne przy function/tool calling i walidacji argumentów).
  - Ułatwiona walidacja: serwer może porównać output modelu z tym schematem i zwracać precyzyjne błędy/diagnostykę.
  - Dokumentacja w promptcie: model widzi nie tylko krótki opis narzędzi, ale także strukturę parametrów.

- Wady / ryzyka:
  - Koszt tokenów: wstrzyknięcie pełnego JSON Schema zwiększa rozmiar promptu (większe użycie tokenów przy każdym wywołaniu). To stoi w sprzeczności z ideą „minimalnego hidden context cost” w sekcji 5.2.
  - Potencjalne zamieszanie modelu: duży, techniczny JSON może wprowadzać hałas do generacji tekstu, zwłaszcza jeśli model nie ma specjalnego mechanizmu function-calling (ale Groq/Llama wspiera to dobrze).

- Wniosek praktyczny: Modyfikacja jest wartościowa dla walidacji i bezpieczeństwa (strong contract). Dla produkcji rekomenduję kompromis:
  - W produkcyjnych, częstych wywołaniach: wstrzykiwać tylko `OPTIMIZED_TOOL_DEFINITIONS` (małe, konkretne instrukcje).
  - W ścieżkach, gdzie spodziewamy się wywołań narzędzi lub chcemy walidować output (np. debug/CI, lub przy pierwszym wywołaniu sesji): wstrzyknąć `toolSchema` lub przekazać go jako metadata (poza kosztownym system prompt).
  - Alternatywa: trzymać `toolSchema` po stronie serwera (nie w promptcie) i wykonywać walidację lokalnie po otrzymaniu odpowiedzi modelu — wtedy nie trzeba zwiększać tokenów.

4) Propozycje skrótów promptu (Ad5) — trzy opcje: pełny, zbalansowany, minimalny

Cel: zachować reguły krytyczne (RAG-only, cytowanie źródeł, format odpowiedzi) i zmniejszyć token cost.

A) Full (obecny) — najlepszy do debug / treningu. Zawiera pełne reguły, przykłady i schema. (najdroższy tokenowo)

B) Balanced (rekomendacja produkcyjna)
- Co zawiera (ok ~25-40% długości pełnego):
  - Krótkie persona: 1–2 zdania (elegancja + forma grzecznościowa)
  - 3 kluczowe zasady: "Używaj TYLKO retrieved_docs", "Cytuj [doc_id]", "Jeśli brak danych powiedz to i zaproponuj 2 kroki"
  - STRUKTURA ODPOWIEDZI w 1 linijce: "Podsumowanie (1 zdanie). Rekomendacja (1-2 zdania). Lista produktów (max 3)."
  - Wstrzyknij `OPTIMIZED_TOOL_DEFINITIONS` (krótkie) — bez pełnego JSON Schema
  - Dodaj `TOOL_RESPONSE_FORMAT_INSTRUCTION` skróconą (najważniejsze: jeśli używasz tool_call -> output JSON blok; else -> reply JSON block)
- Uzasadnienie: zachowuje krytyczne reguły, zmniejsza token cost.

C) Minimal (bardzo niskie token cost, np. dla krótkich zapytań)
- Co zawiera (kilka zdań):
  - 1 linia persona (elegancki doradca)
  - 2 zasady: "Użyj tylko retrieved_docs" i "Cytuj źródła"
  - Wstrzyknięcie krótkich instrukcji tool calling (np. nazwa i wymagane pola) jako pojedyncze linie
  - Brak przykładów, brak pełnego formatowania
- Użycie: szybkie odpowiedzi w dużym wolumenie, ale mniejsza precyzja.

Przykładowy Balanced prompt (proposal — kopiuj/wklej do `worker/src/prompts/luxury-system-prompt-balanced.ts`):

"Jesteś eleganckim doradcą EPIR-ART-JEWELLERY. Udzielaj krótkich, rzeczowych rekomendacji po polsku, używaj form grzecznościowych.
ZASADY: 1) Używaj wyłącznie retrieved_docs (nie halucynuj). 2) Jeśli używasz informacji z retrieved_docs → podaj [doc_id]. 3) Jeśli brak danych → powiedz to i zaproponuj 2 kroki.
STRUKTURA: 1 zdanie powitania, 1-2 zdania rekomendacji, opcjonalnie lista max 3 produktów.
NARZĘDZIA: search_shop_catalog(query, context), get_cart(cart_id), update_cart(cart_id, lines). Jeśli używasz narzędzia → zwróć blok JSON zgodny z TOOL_RESPONSE_FORMAT_INSTRUCTION."
